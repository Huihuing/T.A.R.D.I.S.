# 거래 정합성 계약과 검증

이 문서는 시장가 매매, 지정가 주문, 가상자산 송금 및 보상의 정합성 계약을 설명합니다.
실제 자금 입출금이나 증권 주문 기능을 추가하지 않습니다.

## 시세와 체결

- 표시용 `FinnhubPriceService.getPrice`는 외부 API 장애 때 이전 캐시 가격을 반환할 수 있습니다.
- 신규 시장가/지정가 체결은 `getTradingPrice`만 사용합니다.
- 거래용 가격은 조회 캐시 60초 이내, 공급자 `t` 시각 120초 이내, 미래 시각 오차 30초 이내여야 합니다.
- 누락·비정상 공급자 시각, 만료된 캐시의 갱신 실패, 유효하지 않은 가격은 체결을 보류합니다.
- 시장 종료 후 공급자 시각이 기준을 초과하면 주문을 체결하지 않습니다. 별도 장외 가격 정책은 없습니다.
- DB 잠금을 기다리는 동안 가격이 만료될 수 있으므로 실제 잔액/보유 수량 변경 직전에 재검증합니다.
- 거래용 단가는 현금 총액을 계산하기 전에 HALF_UP 소수 6자리로 정규화합니다. 저장 체결가와 총액에 쓰는 단가가 같으며, 6자리에서 0이 되는 가격은 체결하지 않습니다.

시세를 확인할 수 없는 시장가 주문은 실패하고 지갑·보유 수량·거래 이력·원장을 변경하지 않습니다.
지정가 주문은 유효한 가격이 없거나 잠금 대기 중 가격이 지정 범위를 벗어나면 `PENDING`을 유지합니다.

## 금액과 수량

- 잔액/원장은 `BigDecimal`과 `DECIMAL(19,2)`를 사용하고 HALF_UP으로 센트 반올림합니다.
- 지갑 잔액을 `double`로 바꿨다가 더하기/빼기 후 다시 저장하지 않습니다.
- 체결 총액은 시장 가격을 `BigDecimal.valueOf`로 변환한 뒤 정수 수량을 곱합니다.
- 0센트로 반올림되는 거래는 거부하여 무료 보유 수량 생성을 막습니다.
- 보유 수량 합산은 `long`으로 검사하고 `Integer.MAX_VALUE`를 넘기 전에 거부합니다.
- 평균매입가는 기존 소수 6자리 평균과 시장 가격×수량으로 계산합니다. 현금 총액의 센트 반올림을 평균가 계산에 사용하지 않습니다.
- API 숫자 응답과 일부 평가액/랭킹 계산은 기존 `double` 계약을 유지하므로 매우 큰 값의 화면 표시에는 정밀도 한계가 있습니다. 이는 저장된 잔액/원장을 변경하지 않습니다.

## 트랜잭션과 잠금

시장가 매매와 송금의 HTTP 진입점은 `MutationRequestService`의 트랜잭션 안에서 실행됩니다.
`HTTP >= 400`, `status=FAIL`, 예외가 발생하면 잔액·보유 수량·거래·원장 및 요청 영수증이 모두 롤백됩니다.
송금의 수신 알림도 같은 트랜잭션에 저장되며, 실시간 전송은 기존 `NotificationService`의 commit 이후 전송 규칙을 유지합니다.

- 거래/보상: 회원 → 지갑 → 보유 수량/보상 상태 순서로 write lock을 사용합니다.
- 송금: 두 회원을 username 정렬 순서로 잠근 다음 두 지갑을 잠급니다.
- 지정가 체결: 대기 주문 row를 잠그고 상태를 다시 확인한 뒤 회원/지갑/보유 수량을 잠급니다.
- 지정가 취소와 체결은 같은 주문 row의 write lock으로 최종 상태를 하나로 제한합니다.

## 재전송 계약

대상 API:

- `POST /api/trade/buy`
- `POST /api/trade/sell`
- `POST /api/account/transfer`
- `POST /api/limit-orders`

`Idempotency-Key`는 8~64자이며 영문/숫자와 `._:-`를 허용합니다. UUID를 권장합니다.
키 범위는 JWT 사용자의 username입니다. 키를 다른 API나 다른 주문 내용으로 재사용하면 HTTP 409를 반환합니다.
PIN·비밀번호·토큰은 요청 지문에 포함하지 않습니다.

같은 키와 같은 요청이 동시에 도착하면 DB UNIQUE insert가 먼저 처리하는 트랜잭션의 완료를 기다립니다.
최초 요청이 성공하면 다른 요청은 저장된 HTTP 상태와 JSON 응답을 재생하고 거래를 다시 실행하지 않습니다.
최초 요청이 실패/롤백되면 영수증도 남지 않으므로 같은 키로 다시 시도할 수 있습니다.
서버 재시작 후에도 영수증이 남아 있는 한 같은 계약을 유지합니다.

프론트는 같은 입력의 네트워크 실패/5xx 재시도에 키를 유지하고, 성공하거나 입력이 바뀌면 새 키를 사용합니다.
Production 프론트와의 순차 반영을 위해 키 없는 이전 클라이언트 요청은 허용합니다. 이 경로에는 중복 요청 방지가 적용되지 않습니다.
키 필수화는 수정한 프론트의 운영 반영과 기존 클라이언트 호환 확인 뒤 별도 변경으로 진행합니다.

`V11__mutation_request_receipts.sql`은 영수증 테이블만 추가합니다. 이번 로컬 작업에서 운영 migration은 실행하지 않습니다.
영수증 자동 삭제는 오래된 키의 재전송을 다시 실행할 수 있으므로 도입하지 않았습니다.

## 지정가 스케줄러

기본 최초 실행 대기는 90초이고 실행 사이에는 이전 실행 완료 후 300초를 기다립니다.
한 번에 최대 40종목을 확인하며 종목 이름 cursor와 wrap-around로 다음 실행에서 뒤쪽 종목을 계속 처리합니다.
거래용 시세 장애도 cursor를 진행시키므로 특정 종목의 장애가 후순위 종목을 계속 제외하지 않습니다.
종목이 40개를 넘거나 공급자 장애가 있으면 처리 지연이 추가될 수 있으며 즉시 체결을 보장하지 않습니다.

## 로컬 MySQL 통합 테스트

`TradingIntegrityIntegrationTest`는 실제 MySQL/InnoDB와 Flyway V1~V11, Hibernate `validate`를 사용합니다.
운영 연결을 방지하기 위해 `localhost`/`127.0.0.1` 및 `tardis_audit...` 이름의 DB만 허용합니다.
테스트 전용의 빈 임시 MySQL 8.4를 준비하고 환경변수를 지정합니다. 실제 사용자 데이터가 있는 DB를 사용하지 않습니다.

```powershell
$env:TARDIS_TEST_DB_URL = 'jdbc:mysql://127.0.0.1:<test-port>/tardis_audit'
$env:TARDIS_TEST_DB_USERNAME = '<test-user>'
$env:TARDIS_TEST_DB_PASSWORD = '<test-password>'
cd Backend
.\gradlew.bat test --tests '*TradingIntegrityIntegrationTest' --no-daemon
```

환경변수가 없으면 이 통합 테스트는 skip됩니다. 일반 unit test 성공을 실제 MySQL 검증 성공으로 해석하지 않습니다.
검증 범위는 동시 매수/매도, 동시 중복 매수/송금/지정가 생성, 반대방향 송금, 원장/알림 실패 시 rollback,
지정가 중복 체결/취소 경합, 잠금 이후 시세 만료, 큰 잔액의 센트 보존, 평균가 정밀도, 수량/0센트 경계입니다.
테스트 결과 개수와 운영 배포 검증은 해당 작업의 감사 보고서에서 확인합니다.
